## 2. 中等问题 (会影响生产,优先级 🟡)

### M1. PRAGMA 设置在 pool 单连接初始化时,但只对新连接生效

**位置**: `python/soloforge_ai_society/database/pool.py:76-82`

```python
conn.execute("PRAGMA journal_mode = WAL")  # 只对新 conn 生效
conn.execute("PRAGMA cache_size = -65536")
```

**问题**: 如果 DatabaseManager 重启时旧 sqlite 连接还持有,**WAL 模式不切换**。SQLite PRAGMA 是**连接级**,需要每个 connection 都要设置。

**当前实现**: 每个 conn 都调一次,所以新连接都对 ✓。但**如果有人用 raw sqlite3.connect 而不走 pool**,PRAGMA 不生效。

**修复**: 加 SQLite URI 模式强制 (`?journal_mode=WAL&cache_size=-65536`) 或在 manager.py 加 startup-time WAL checkpoint 验证。

**M1 修复状态 (2026-07-01)**:
- ✅ 函数式强制: `soloforge_ai_society/database/pool.py` 已加 `apply_p6_baseline()` 和 `verify_pragma_alignment()`, 7 个 PRAGMA (journal_mode / synchronous / cache_size / mmap_size / temp_store / foreign_keys / busy_timeout) 一次性设置
- ✅ 批量应用到生产路径 (本次 4 文件 7 处修复):
  - `reputation_sync_receiver.py:_acquire_new_connection` (8766 pool, 之前手动只设 2 个)
  - `database/migration.py:migrate()` (line 412) + `get_status()` (line 466)
  - `database/health.py:check()` + `get_performance_metrics()` + create_backup schema 验证 + `restore_from_backup()`
- ⏭️ 未修 (非生产路径): init_ai_society.py / db_cli.py / 各种 e2e+test (一次性, 修了无收益)
- 验证工具:
  - `python/tools/m1_pragma_uri_test.py` (PASS) — 函数 + manager 集成
  - `python/tools/m1_pragma_all_paths_test.py` (PASS 7/7) — 全生产路径覆盖
- URI 模式在 Windows + sqlite3 3.53.1 上不生效, 实际方案是 `apply_p6_baseline()` 函数式

### M2. `reputation_sync_log` 表 ON CONFLICT 增量逻辑可能负数

**位置**: `reputation_sync_receiver.py:91`
```sql
current_reputation_score = current_reputation_score + excluded.current_reputation_score
```

**问题**: `excluded.current_reputation_score` 是 SQLAlchemy/ON CONFLICT 表达式的"被排除行"的值,但 INSERT VALUES 里我们传的是 `increment_value` (increment),**不是 current_score**。如果 receiver 同时收到正+负 increment,语义是对的;但**如果两次同一 cluster_id,值累加正常,如果负值 + 重复重试,会越扣越多**。

**修复**: 改用 `INSERT ... ON CONFLICT DO UPDATE SET current_reputation_score = max(0, current_reputation_score + excluded.current_reputation_score)`,或加幂等键 `command_id UNIQUE`。

**M2 修复状态 (2026-07-01)**:
- ✅ MAX(0,...) 防负值 — 已在 audit 修复批次完成
- ✅ 幂等键 (新加 `reputation_sync_log_event_dedup` 表, `command_id TEXT PRIMARY KEY`)
  - 同一 commandId 重放 → HTTP 200 `{"ok":true,"deduped":true}`, SQLite score 不变
  - 不同 commandId 同 cluster → 各自累加, 业务语义保留
  - 验证工具: `python/tools/m2_idempotency_e2e_test.py` (PASS)
  - 涉及文件: `python/soloforge_ai_society/services/reputation_sync_receiver.py`

### M3. p9 outbox worker 没限流 — 一次性取 batch_size 条会耗尽 DB

**位置**: `outbox.ts:225` 循环 `for r of records` 串行处理

**问题**: `batch_size=100` + `poll=100ms` = 1000 条/s,每条 fetch() 3s timeout → 最坏 1000 * 3s = 3000s 并行堵塞。**实际串行处理**,所以 1s 能处理 ~3 条,但 poll 间隔 100ms,**新的 tick 永远不会 fire** (因为 _scheduleNext 在 finally 里)。

**修复**: 加并发限制 `p-limit` 或改 worker 配置 batch_size=10。

### M4. badger-gateway BatchedWriter put 失败后**默默丢消息**

**位置**: `python/soloforge_ai_society/services/badger_grpc_client.py:435-444`
```python
except BadgerGatewayError as e:
    self.total_errors += 1
    logger.error(f"BatchedWriter flush failed: {e}")
    return 0
```

**问题**: flush 失败后 batch 内容**完全丢失**,不进 outbox 也不重试。压测时 errors=0 所以测不到,生产 AI Society 断了就丢。

**修复**: 失败时 batch 写本地 fallback (临时文件),下次 restart 再 retry。
