# 代码审查

## 概述

以"读者"视角系统性地审查代码。关注 **正确性 > 安全性 > 性能 > 可维护性**。

## 审查清单

### 1. 正确性
- [ ] 是否处理了所有边界情况(空/极大/极小/null/undefined)?
- [ ] 异步操作是否正确 await?
- [ ] 数值计算是否会溢出/精度丢失?
- [ ] 字符串拼接是否考虑了 Unicode?
- [ ] 状态修改是否在正确的时机发生?
- [ ] 并发访问是否有锁/race condition?

### 2. 安全性
- [ ] 是否有 SQL 注入风险(原始拼接)?
- [ ] 是否有 XSS 风险(未转义的用户输入)?
- [ ] 是否有路径穿越(用户输入拼路径)?
- [ ] 是否有敏感信息泄露(日志/错误信息)?
- [ ] 是否有不当的权限校验缺失?
- [ ] 命令执行/eval 是否限制了来源?

### 3. 性能
- [ ] 是否有 N+1 查询?
- [ ] 是否在循环内做了 I/O?
- [ ] 是否可以不必要地复制大对象?
- [ ] 是否有未缓存的重复计算?
- [ ] 算法复杂度是否合理?(O(n²) → O(n log n))

### 4. 可维护性
- [ ] 命名是否清晰自解释?
- [ ] 是否有重复代码可抽取?
- [ ] 函数是否过长(>50 行考虑拆分)?
- [ ] 是否有"魔法数字"应改为常量?
- [ ] 错误信息是否对调试友好?
- [ ] 是否补充了必要的注释?

### 5. 测试
- [ ] 是否有对应测试?
- [ ] 测试是否覆盖了主要分支?
- [ ] 测试是否易读?

## 输出格式

按"严重程度 + 位置 + 建议"组织:

```
🔴 必须修复(阻塞)
- src/api.ts:42 SQL 拼接,需用参数化查询

🟡 建议修复(可优化)
- src/utils.ts:15 可缓存,避免每次重算

🟢 锦上添花(可选)
- src/index.ts:8 命名 `tmp` 不够清晰,建议 `requestId`
```

## 审查原则

- **不挑刺挑细节**:关注真正影响可读性/正确性的问题
- **不重复造轮子**:项目已有规范时不要引入新风格
- **给方案不只给问题**:提出具体修改建议
- **区分 NIT/MUST/SHOULD**:让作者知道优先级
